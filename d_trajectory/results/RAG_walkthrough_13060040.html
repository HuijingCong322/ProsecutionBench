How our examiner RAG works, one case at a time

We follow one real patent application, 13060040, from the raw download to a prediction. Every file name, text excerpt, number and score here is real, taken from A's data, B's new BGE-M3 package and D's code. The mentor asked that we can say, for every step, what goes in, what comes out, where it lives and why. This page does that.

Which tasks this example uses. The example predicts D's three trajectory tasks: Disposition, Remaining Rounds and Time to Next Action. The other tasks (B's next action and grounds, C's examination generation) use the same setup. Steps 1 to 4 (the query, the library, the search, the top 3) are shared by everyone. Only Steps 5 and 6 change: what we read from the 3 past applications, and what the prompt asks. The table in Part 5 shows the differences.

1 · Basic ideas first

What are we predicting?

We take one application and stop the clock on a fixed day, the cutoff. For us the cutoff is the day the applicant filed the first reply to the examiner's first rejection. For 13060040 that is 2014-09-26. Then we ask what happens next.

TaskQuestionReal answer for 13060040 (hidden from every method)
DispositionWill it be allowed or abandoned, and when? Probabilities for months 1–24Abandoned on day 766, so still pending at month 24
Remaining RoundsHow many more rejections before it ends?4
Time to Next ActionHow many days until the examiner's next letter?73 (a final rejection on 2014-12-08)

Anything dated after the cutoff is the answer and is never used as input. This is the cutoff rule.

What is a prompt?

A prompt is one long text message we send to the LLM (GPT-5-mini). The LLM reads it and writes an answer back. It cannot open folders or search anything; it only sees what we paste into that message.

What is RAG?

RAG means Retrieval-Augmented Generation. Before we ask the LLM, a separate program searches a library and picks the few documents most relevant to the question. We paste those documents into the prompt, and then the LLM answers. It works like an open-book exam where a librarian hands you the three most useful books first. The librarian is an ordinary program; the student is the LLM.

So RAG always has two separate parts:

  1. Retrieval (the search). A Python program with no LLM. It takes a question text and a library, and returns a short list of the most similar items.
  2. Generation (the answer). The LLM call. The items found by the search are pasted into the prompt.

For us, the library is the examiner's own past applications and the question is what this new case is about. The idea is that an examiner may treat similar inventions in a similar way, so how their similar past cases went may hint at how this one will go. That is what "personalization" means here.

What are an embedding and a similarity score?

  • An embedding model turns a piece of text into a fixed list of numbers. We use BGE-M3, which gives 1,024 numbers per text. Texts about similar things get similar lists. The model does nothing else; it does not answer questions.
  • The similarity score (cosine) compares two lists and gives one number. Higher means the two texts are about more similar things. Between our patents it lands roughly between 0.5 and 0.8.
  • TF-IDF is an older method that only checks which words two texts share. We used it before; the mentor asked us to replace it with embeddings, and B has done that.

Words we use

WordMeaning
QueryThe text that describes the case we predict. It is used only inside the search program, to search with. It is not the prompt.
LibraryThe examiner's past applications that the search program looks through.

AbstractThe one-paragraph summary of an invention, as published.

"Should we feed the raw PDF?" The PDF and its text version contain the same words, and an LLM reads text anyway; a PDF is converted to text before the model sees it. Feeding whole files is not practical either: three past applications run to hundreds of pages, much of it forms and boilerplate.

Each past application has its own folder with the same kinds of files as Step 1: an event log, a published abstract, published claims and the letters. Only things dated before our cutoff are included, and no application shares a family with our 1,000 cases.

For each past application, B builds a text the same way as the query: its abstract + claims, dated no later than its first usable reply. All 30 are optical body sensors. None is a drug-delivery device like our case. Keep this in mind for Step 4.

STEP 4

Input → output
Query + 19 texts → table ranking_top3_links_before_review.csv

Purpose: out of the 19 searchable past applications, find the 3 whose inventions are most like our case.

What the program does:

  1. BGE-M3 turns each text into 1,024 numbers. A long text is cut into pieces the model can read (up to 8,190 tokens each); each piece becomes numbers, and the pieces are averaged. Nothing is thrown away.
  2. It computes the similarity score of each past application with the query.
  3. It sorts by score, keeps at most one application per patent family, and takes the top 3.
# the core of it
model  = SentenceTransformer("BAAI/bge-m3")                     # fixed version 5617a9f6…
q      = model.encode(query_text, normalize_embeddings=True)    # our case → 1,024 numbers
P      = model.encode(past_texts,  normalize_embeddings=True)    # 19 past applications → 19 × 1,024
scores = P @ q                                                   # 19 similarity scores
top3   = pick_top(scores, k=3, one_per_family=True)

12109224 (coupling a channeled sample probe to tissue, 0.695) was skipped because it is the same family as rank 2. The least similar of the 19 scored 0.552.

Old top 3 (TF-IDF on letters)

12109224 probe coupling · 12495545 ear sensor · 12345537 pulse oximeter

New top 3 (BGE-M3 on abstract + claims)

None of the three is the same. The old and new scores use different scales and cannot be compared with each other.

"Most similar" is not the same as "similar". All 19 past applications score between 0.55 and 0.71. They are all medical sensing devices, roughly as close to a drug-delivery device as each other.

The wrong examiner's top 3 (another examiner of the same art unit) score 0.70, 0.70 and 0.69, as high as our own examiner's. Across all 100 cases, the best match has a median score of 0.75 and the worst a median of 0.58.

So for this case the top 3 is only slightly better than any 3 of this examiner's applications.

6 · What D runs this week (profile_with_embedding), and why

  1. No LLM first (free), on the same 100 cases:
    • the top-3 average (Step 6a) against the examiner's full-history numbers (the statistics card): are the 3 most similar past applications better than the examiner's whole history? This is the mentor's hypothesis.
    • the same top-3 average with the wrong examiner: is it about this examiner?
  2. Then the LLM, with the three blocks of Step 6b (card, paths, fulldoc), each for the own and the wrong examiner. The main question: does the LLM given the 3 applications in full beat the top-3 average of the same 3? It must, to show that it reads the cases rather than repeating numbers.
  3. Next meeting: this page, the code, and this one case run live.

If similar cases do not help, we will say why. Case 13060040 is a drug-delivery device, and its examiner's history holds only optical sensors, so no truly similar past case exists. The mentor asked for exactly this: if it doesn't work, explain why it doesn't.
